## Fase 3 — Integraciones externas

- [x] Integración con Google Calendar: exportación puntual de tareas completadas como registro histórico (con hora de inicio real y duración real) — vía URL de `calendar.google.com/render`, sin OAuth ni API key
- [x] Al completar una tarea, preguntar si se quiere abrir en Google Calendar con los datos precargados
- [x] Al completar una tarea repetible, sugerir la próxima fecha y crear la siguiente instancia — resuelto desde la ronda de mantenimiento cíclico (v0.3.0), había quedado listado acá también por error
- [x] Atributo de ubicación geográfica asociado a una tarea — **rediseñado**: en vez de texto libre (como había quedado en v0.9.0), ahora es una entidad propia con ABM (vista "Ubicaciones", nombre + latitud + longitud), y las tareas referencian `ubicacion_id`. Badge y filtro manual en Tareas/Hoy siguen igual que antes pero sobre esta entidad. Sigue **sin GPS** — las coordenadas se cargan a mano una vez por ubicación
- [x] Validación de condiciones climáticas: checkbox `requiere_clima_bueno` por tarea; en Hoy y en las vistas de 3/8 días se consulta el pronóstico real (Open-Meteo, gratis, sin API key) usando las coordenadas de la ubicación de la tarea, y si la probabilidad de lluvia es alta se muestra un aviso para posponerla
- [x] Evaluar opciones técnicas de sincronización multi-dispositivo (ver sección "Sync — opciones a evaluar" abajo): se eligió e implementó la **opción 2 (Google Drive API vía OAuth)** — es la única de las 4 que resuelve el uso desde el celular (la carpeta local vía File System Access API no funciona en navegadores móviles) sin contradecir "sin backend/servidor de pago" (se descartó la opción 3 por eso). Nuevo módulo `assets/js/google-drive-sync.js` (mismo patrón que `google-calendar.js`, scope propio `drive.file` — la app solo ve archivos que ella misma crea, no todo el Drive), un único archivo JSON remoto (`super-todo-list-datos.json`) con el `estado` completo. Botón "Sincronizar con Google Drive" en la cabecera. **Limitaciones aceptadas para este primer paso**: el token no se persiste entre sesiones (hay que reconectar en cada pestaña/sesión nueva, igual que Calendar); sin merge automático de conflictos — si el archivo remoto cambió por fuera desde la última sincronización conocida de este dispositivo, se le pregunta al usuario con un `confirm()` cuál versión conservar antes de pisar nada
- [x] Integración con Google Calendar: lectura de eventos existentes para detectar solapamientos. A diferencia de la exportación (sin OAuth), leer eventos sí requiere autenticarse: se usa Google Identity Services (login en popup, primera dependencia externa vía `<script>` del proyecto) con el flujo de token client (scope de solo lectura), token guardado en memoria (no se persiste, expira en ~1h y se vuelve a conectar con un click). Nuevo botón "Conectar con Google Calendar" en la vista Hoy; las tareas con `fecha_hora_agendada` que se superponen con un evento real de hoy muestran el aviso "📅 Se superpone con...". La app de OAuth queda en modo "Testing" en Google Cloud Console (solo funciona con la cuenta agregada como test user)
- [x] Filtro de "ubicación actual" unificado: nuevo módulo `assets/js/ubicacion-actual.js` (mismo patrón que el tema claro/oscuro — clave propia de `localStorage`, no pasa por `estado`/Drive/carpeta) reemplaza las dos variables de filtro independientes que ya existían en Hoy y Tareas. Ahora Hoy, Tareas y 3/8 días comparten la misma "ubicación actual": elegirla desde cualquiera de las tres se refleja en las otras sin recargar, y persiste entre recargas de página (antes se reiniciaba). Semana y Gantt quedan fuera de este alcance (son vistas de planificación, no de triage por ubicación)
- [ ] Lectura de eventos pasados de Google Calendar para estimar tiempos/recursos de tareas similares futuras — **priorizado para una próxima ronda**, antes de v1.0.0

## Fase 4 — Inteligencia e informes

- [x] Roadmap de objetivos — versión manual: nueva entidad Meta (corto/mediano/largo plazo) con ABM en la vista "Metas", que muestra progreso (tareas completadas/asociadas) con barra simple. Las tareas se asocian a una o varias metas desde el panel "Metas" en la vista Tareas. La versión con IA que arma hitos automáticamente queda en el ítem de abajo
- [x] Capa opcional de IA conectable — primer paso (arme de subtareas a partir de una meta): nuevo módulo `assets/js/ia-conectable.js` + botón "Sugerir tareas con IA" en cada meta (vista Metas), que arma un prompt para copiar/pegar en un LLM externo (ChatGPT, Claude, etc.) y permite pegar la respuesta (JSON) de vuelta, previsualizar y agregar las tareas propuestas seleccionadas. 100% manual, sin llamar a ninguna API — el core sigue sin depender de tokens de LLM
- [x] IA conectable — reestructurar prioridades de todas las tareas: nuevo botón "Reestructurar prioridades con IA" en la vista Tareas, mismo mecanismo de prompt/respuesta manual que la sugerencia de subtareas; arma un prompt con las tareas accionables actuales (id/nombre/categoría/fecha límite/importancia), y al pegar la respuesta (JSON) previsualiza solo los cambios reales de importancia para aplicar de forma selectiva
- [x] Chatbot para dialogar y definir metas/objetivos de vida — primer paso: nuevo botón "Definir meta charlando con IA" en la vista Metas. Mismo flujo manual de copiar/pegar que el resto de la capa de IA conectable, pero de ida y vuelta: cada mensaje se agrega a una conversación en memoria que se reenvía completa en cada prompt (el LLM externo no tiene memoria entre turnos), hasta que el usuario decide "Finalizar" y la IA devuelve un JSON con los datos de la meta (nombre/plazo/fecha objetivo/descripción) para crearla. No hay seguimiento conversacional posterior a la creación
- [x] Informes básicos: nueva vista "Informes" con tabla de completadas (últimos 7 días) vs. pendientes actuales por categoría, y promedio de duración estimada vs. real
- [x] Índice de procrastinación — versión proxy: tareas actualmente pospuestas al menos una vez (`motivo_incumplimiento` cargado y sin completar) contra completadas en los últimos 7 días. No es un histórico real de reprogramaciones (el modelo no guarda ese log todavía); si hace falta más precisión, una ronda futura puede sumar un registro de eventos
- [x] Métrica de throughput (capacidad de trabajo, estilo Kanban): nueva sección "Throughput semanal" en Informes — gráfico de barras con tareas completadas por semana (últimas 8 semanas) y el promedio semanal, calculado al vuelo sobre `completada_en`

## Fase 5 — Móvil y UX avanzada

- [x] Versión PWA — primer paso: `manifest.json` + ícono SVG (instalable como app) y `sw.js` (service worker con estrategia network-first, cae a caché solo sin conexión — deliberadamente no cache-first para no interferir con el desarrollo activo)
- [x] PWA — precachear el app shell explícitamente: `sw.js` precachea en `install` la lista `ARCHIVOS_PRECACHE` (app shell completo), así la primera carga offline sin visitas previas también funciona. La lista se mantiene a mano (sin build tools); `AGENTS.md` documenta sumar ahí cualquier archivo nuevo de `assets/js/`/`views/`
- [x] Notificaciones — primer paso (locales, no push real): como la app no tiene backend ni servidor propio, un Web Push real (VAPID + push service, con la app cerrada) no es viable. En su lugar, `assets/js/notificaciones.js` revisa cada 60s (mientras la app está abierta, aunque sea en una pestaña de fondo) si hay tareas con `fecha_hora_agendada` a menos de 10 minutos, y dispara una notificación del navegador vía el service worker (`registration.showNotification`). Nuevo botón "Activar notificaciones" en la cabecera para pedir el permiso; nuevo campo `notificada_en_para` en Tarea para no repetir avisos; click en la notificación enfoca/abre la app (`sw.js` maneja `notificationclick`)
- [ ] Evaluar si conviene convertir el sistema en un integrador más amplio: calendario propio (+ conexión opcional a Google Calendar) y administración económica personal (gastos, movimientos, inversiones, saldos, metas de ahorro, cheques) — **postergado a después de v1.0.0**, una vez validado el core de tareas con uso real
- [x] Rediseño visual + modo claro/oscuro: no estaba en el backlog original, pedido directo del usuario. `assets/css/main.css` ya centralizaba casi todos los colores en variables CSS (`:root`), así que redefinirlas alcanzó para re-temear toda la app sin tocar cada vista. Nuevo botón de tema en la cabecera (`index.html`/`app.js`), preferencia guardada en `localStorage` (clave separada de los datos de la app) y con fallback automático a `prefers-color-scheme` del sistema si el usuario no eligió nada todavía. Retoques de modernización: transiciones suaves, hover con elevación en tarjetas/items, nav con estilo "pill". De paso se corrigió un bug de cascada preexistente donde `.etiqueta-fecha` (definida más abajo en el archivo) le ganaba a los colores especiales de las etiquetas "Agendada"/mantenimiento/clima/solapamiento de calendario, que nunca se habían mostrado correctamente

## Sync — opciones a evaluar (Fase 3+)

Registro de la inquietud original del usuario sobre cómo sincronizar datos entre 2 PCs y 1 celular sin depender de un servidor de pago. Para la Fase 1 se resolvió con **carpeta de Google Drive local + File System Access API** (ver [SPEC.md](SPEC.md)); desde v0.51.0 se usa la **opción 2 (Google Drive API)** como único destino. Opciones registradas:

1. **Carpeta sincronizada por el cliente de escritorio de Drive** (descartada en v0.51.0): simple, sin OAuth, pero requiere que el navegador soporte File System Access API (Chrome/Edge) y que la carpeta esté físicamente sincronizada en cada dispositivo.
2. **Google Drive API (OAuth)** (implementada en v0.51.0): sync real sin depender de que la carpeta esté sincronizada localmente; permite uso desde el celular vía navegador. Suma complejidad de autenticación y manejo de conflictos (ETag / última modificación).
3. **Backend propio liviano** (ej. FastAPI/Node) con base de datos simple (SQLite) expuesto solo en red local o con túnel — da concurrencia real pero contradice el requisito de "sin servidor de pago" y suma una pieza más para mantener.
4. **Formato de archivo**: evaluar si conviene mantener un único JSON o fragmentarlo (por año, por categoría) a medida que crezca el volumen de datos.
