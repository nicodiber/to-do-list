## Problemática

Una persona no logra cumplir tareas y por consiguiente sus metas, y le dedica mucho tiempo a su autogestión de tareas para cumplir sus objetivos.

## Propuesta

Plataforma digital tipo "to do list" con asistente donde usuario carga sus tareas y objetivos, donde sistema ordena las tareas permitiendo al usuario realizarlas en orden de mayor conveniencia.

## Nombre del Proyecto: Super To-Do List (Gestor Integral de Vida)

### 1. Visión General del Proyecto
**Propósito:** Desarrollar una plataforma digital de autogestión de tareas y objetivos diseñada para optimizar el tiempo, reducir la procrastinación y facilitar la ejecución de proyectos personales y profesionales.
**Problema a resolver:** El usuario pierde tiempo replanificando tareas ante imprevistos, le cuesta identificar las tareas más urgentes/importantes para accionar inmediatamente, y las herramientas actuales (Google Calendar, Notion, Tasks) están fragmentadas, son pesadas, o no ofrecen automatizaciones inteligentes adaptadas a su estilo de vida.
**Público Objetivo:** Inicialmente, el propio desarrollador/usuario (estudiante universitario, profesional, con múltiples proyectos y hobbies). Escalable a futuro para compartir o comercializar.

### 2. Principios y Filosofía del Sistema
El sistema debe incorporar y automatizar metodologías de productividad:
- **El tiempo es irrecuperable:** Enfoque en la acción inmediata y automatización de la replanificación.
- **Hábitos Atómicos:** Desglose de grandes objetivos en hitos y subtareas pequeñas.
- **Principio de Premack (Tarea fea x Tarea linda):** Restringir recompensas (ej. entretenimiento) hasta cumplir tareas de alta fricción.
- **Regla 80/20 (Pareto):** Identificación del 20% de tareas que generan el 80% del impacto.
- **Fail Fast (Corregir rápido):** Al fallar una tarea, el sistema indaga el motivo y replanifica inmediatamente sin culpa.
- **Métricas Ágiles (Scrum/Kanban):** Medición del *Throughput* (capacidad de trabajo), sprints adaptados al individuo.

### 3. Requisitos Funcionales (FR)

#### 3.1. Gestión de Datos (ABM - Alta, Baja y Modificación)
- **Categorías:** Capacidad de crear áreas de vida (Personal, Académica, Trabajo, Emprendimiento, Dependiente de Persona/Ubicación).
- **Subcategorías:** Jerarquía dentro de categorías (ej. Personal -> Hobbie, Académica -> Asignaturas).
- **Tareas y Subtareas:** Soporte para N-niveles de anidamiento. Las tareas deben heredar propiedades o autocompletarse según la jerarquía o historial.

#### 3.2. Modelo de Datos de la Tarea (Atributos)
Cada tarea debe contener:
- `ID`: Identificador único.
- `Nombre`: Título de la tarea.
- `Estado`: `a confirmar`, `pendiente`, `en progreso`, `completada`.
- `Categoría / Subcategoría`: Enlace a jerarquía.
- `Fecha de Inicio (Earliest Start Date)`: A partir de cuándo se *puede* hacer.
- `Fecha Fin (Deadline)`: Cuándo *debe* estar completada obligatoriamente.
- `Fecha Sugerida`: Fecha recomendada (opcional).
- `Duración Estimada`: En bloques de 15 minutos.
- `Divisible`: Booleano. `True` = se puede pausar y retomar; `False` = debe completarse de principio a fin en una sentada (Default).
- `Días Hábiles`: Días de la semana permitidos para esta tarea (ej. solo fines de semana para motociclismo).
- `Costo Monetario`: Valor estimado/real asociado.
- `Ubicación / GPS`: Coordenadas o etiqueta de lugar asociado.
- `Condición Climática`: Requisito del clima para su ejecución.
- `Recursos Asociados`: Enlaces a documentos, notas, procedimientos estandarizados.
- `Recompensa`: Valor o actividad de recompensa ligada a la tarea.

#### 3.3. Tipos Especiales de Tareas
- **Tareas de Mantenimiento (Cíclicas adaptativas):** No desaparecen. Al completarse, su próxima fecha se calcula sumando el intervalo (ej. 1 mes) a la *fecha de finalización real*, no a la fecha teórica.
- **Tareas Concatenadas (Dependencias):** Tareas que bloquean/desbloquean otras. (Ej. Comprar verdura -> Limpiar verdura -> Congelar). Si la primera se pospone, las dependientes se desplazan automáticamente.
- **Tareas de Multitasking vs. Foco:** Etiquetado para permitir agrupar tareas que no requieren 100% de atención (ej. ver una clase teórica pasiva mientras se ordena el cuarto).

#### 3.4. Vistas e Interfaz de Usuario (UI)
- **Vista de 1 Día (Hoy):** Foco extremo. Separación estricta entre:
  1. Tareas Obligatorias del día.
  2. Tareas No Obligatorias (ordenadas por prioridad/tiempo libre).
- **Vista de 3 Días:** Corto plazo para prever cuellos de botella.
- **Vista de 8 Días:** Mediano plazo (semana extendida).
- **Autocompletado Predictivo:** Al tipear una nueva tarea, sugerir atributos basados en tareas pasadas similares.

#### 3.5. Ciclo de Vida y Asistente (Feedback Loop)
- **Cierre de Tarea / Día:** Sistema interactivo que pregunta:
  - ¿Se cumplió? Si no, ¿por qué?
  - Si se cumplió, solicitar duración real (para mejorar estimaciones futuras).
  - Si no se cumplió, sugerir reprogramación.
- **Atajos de Reprogramación:**
  - `Mañana` = 07:00 h
  - `Tarde` = 12:00 h
  - `Tardecita` = 17:00 h
  - `Noche` = 20:00 h
  - `Próximos X días`, `Primer [Día] del mes`.
- **Mejora Continua:** Para tareas repetitivas, preguntar qué se puede mejorar en el procedimiento para la próxima vez.

#### 3.6. Objetivos a Largo Plazo y Proyectos
- **Roadmapping:** Relacionar tareas individuales con Metas/Propósitos (corto, mediano, largo plazo).
- **Generación de Hitos:** Capacidad del sistema para estructurar un objetivo grande en fases.

#### 3.7. Integraciones y Automatizaciones
- **Google Calendar:**
  - Al completar tarea, opción de exportar como evento histórico en Calendar con hora de inicio y duración real.
  - Lectura del calendario para identificar disponibilidad y evitar solapamientos.
- **Clima:** Validación de pronóstico meteorológico para tareas dependientes del clima al momento de sugerir fechas.
- **GPS (Futuro móvil):** Notificación por proximidad geográfica.

#### 3.8. Informes y Gamificación
- **Métricas:** Resúmenes semanales (Propuesto vs. Hecho), Índice de Procrastinación, Throughput.
- **Social:** Comparación de Throughput con amigos. Avisos de sociabilización (ej. "Hace X tiempo no te reúnes con Y persona").

### 4. Requisitos No Funcionales (NFR)

#### 4.1. Arquitectura de Almacenamiento y Sincronización (Sin costo)
- **Estrategia Desacoplada:** El motor/lógica del sistema estará separado de los datos.
- **Base de Datos:** Almacenamiento en archivos estandarizados estructurados (ej. `.csv` o `.json`).
- **Sincronización:** Uso de carpetas sincronizadas en la nube (Google Drive o Dropbox) para permitir el acceso desde 2 PCs (32GB y 16GB de RAM) y 1 Celular sin necesidad de un servidor de base de datos de pago.

#### 4.2. Rendimiento e Infraestructura
- **Eficiencia:** Debe ser una aplicación ligera (Lightweight). Solucionar el problema de lentitud experimentado con Google Calendar en equipos de 16GB RAM.
- **Formatos Estándar:** Fechas en formato `DD/MM/YYYY`, Horarios en 24 horas (`UTC-3`).

#### 4.3. Inteligencia Artificial (LLM)
- **Core Independiente:** El sistema base **no debe depender** de tokens de IA para su funcionamiento crítico.
- **Capa de Asistencia (Opcional):** Un módulo conectable a APIs de LLM que pueda leer los `.csv`/`.json` y proponer:
  - Estructuras de proyectos.
  - Identificación de patrones de procrastinación.
  - Generación de diálogos tipo Chatbot para definir metas de vida.

### 5. Fases de Desarrollo Sugeridas
- **Fase 1 (MVP Local):** Estructura de datos (CSV/JSON), ABM básico de tareas y subcategorías, vistas de listas simples y atributos fundamentales. Sincronización cruda por Drive.
- **Fase 2 (Lógica de Tiempo y Estados):** Implementación de dependencias (tareas que desbloquean otras), atajos de reprogramación, tareas cíclicas y cálculos de fechas.
- **Fase 3 (Integraciones):** Exportación e importación con Google Calendar, uso de API del clima.
- **Fase 4 (Inteligencia e Informes):** Integración de capa LLM para análisis, sistema de informes de throughput, gamificación.
- **Fase 5 (Móvil y UX Avanzada):** Aplicación PWA o móvil nativa para notificaciones GPS.

### 6. Consideraciones para el LLM Agéntico (Desarrollador de Código)
Al momento de generar el código, el agente deberá:
- Definir las clases/interfaces base asegurando la estructura exacta del Modelo de Datos (Sección 3.2).
- Diseñar la capa de persistencia asegurando concurrencia básica o manejo de conflictos (ya que Drive/Dropbox pueden generar versiones en conflicto si se edita desde celular y PC simultáneamente).
- Separar estrictamente el Frontend del Backend lógico para permitir interfaces en consola, web o móvil consumiendo el mismo núcleo en Python/JS.

### 1. Visión General del Proyecto
**Propósito:** Desarrollar una plataforma digital de autogestión de tareas y objetivos diseñada para optimizar el tiempo, reducir la procrastinación y facilitar la ejecución de proyectos personales y profesionales.
**Problema a resolver:** El usuario pierde tiempo replanificando tareas ante imprevistos, le cuesta identificar las tareas más urgentes/importantes, y las herramientas actuales están fragmentadas, son pesadas o carecen de automatizaciones a medida.
**Público Objetivo:** Inicialmente, el propio desarrollador/usuario. Escalable a futuro.

### 2. Principios y Filosofía del Sistema
- **El tiempo es irrecuperable:** Acción inmediata y automatización de la replanificación.
- **Hábitos Atómicos:** Desglose de objetivos en hitos y subtareas.
- **Principio de Premack:** Restringir recompensas hasta cumplir tareas de alta fricción.
- **Regla 80/20 (Pareto):** Identificación de tareas de alto impacto.
- **Fail Fast:** Al fallar, el sistema indaga el motivo y replanifica.

### 3. Requisitos Funcionales (FR)

#### 3.1. Gestión de Datos (ABM - Alta, Baja y Modificación)
- **Estructura Jerárquica:** Categorías -> Subcategorías -> Tareas -> Subtareas (N-niveles).

#### 3.2. Modelo de Datos de la Tarea (Esquema JSON)
Cada tarea/nodo debe contener:
- `ID`: Identificador único (UUID).
- `Nombre`: Título de la tarea.
- `Estado`: `a confirmar`, `pendiente`, `en progreso`, `completada`.
- `Jerarquía`: Enlace a categoría/subcategoría o `parent_ID`.
- `Fechas`: `inicio_posible` (Earliest Start Date), `fecha_limite` (Deadline), `fecha_sugerida`.
- `Duracion_estimada`: En bloques de 15 minutos.
- `Divisible`: Booleano (Default: `False`).
- `Dias_habiles`: Array de días permitidos (ej. `["sábado", "domingo"]`).
- `Mantenimiento`: Objeto con reglas de ciclicidad (ej. `{ "intervalo": "30d", "desde": "ultima_finalizacion" }`).
- `Dependencias`: Array de `ID`s que deben completarse antes de habilitar esta tarea.
- `Multitasking_Foco`: Etiqueta de nivel de atención.
- `Atributos Extra`: Costo, GPS, Clima, Recursos, Recompensa.

#### 3.3. Vistas e Interfaz de Usuario (UI)
- **Vista de Calendario (Time-blocking):** Grilla visual estilo Google Calendar propia del sistema para ver cómo se distribuyen las tareas estimadas en el día/semana.
- **Vista de Foco (1 Día / Hoy):** Tareas Obligatorias vs. No Obligatorias ordenadas por prioridad.
- **Vistas a Mediano Plazo:** 3 días y 8 días.
- **Autocompletado Predictivo:** Sugerencias basadas en historial.

#### 3.4. Ciclo de Vida y Replanificación
- **Asistente de Cierre:** Preguntas interactivas al terminar un bloque de tiempo o día (cumplimiento, motivos, duración real, mejoras).
- **Atajos de Reprogramación:** `Mañana` (07:00), `Tarde` (12:00), `Tardecita` (17:00), `Noche` (20:00), `Próximos X días`.
- **Desplazamiento en Cascada:** Al posponer una tarea, reprogramar automáticamente las tareas dependientes.

#### 3.5. Integraciones Externas
- **Google Calendar API:**
  - *Lectura (Read-only):* Obtener eventos existentes para advertir sobre solapamientos en la Vista de Calendario propia.
  - *Escritura (Exportación puntual):* Botón manual para enviar tareas completadas/agendadas a Google Calendar como registro histórico.
- **Google Drive API:** Sincronización del archivo de base de datos `.json`.

### 4. Requisitos No Funcionales (NFR)

#### 4.1. Arquitectura del Sistema
- **Tipo de Aplicación:** Web App Local (Frontend + Backend ligero local) para uso en escritorio.
- **Acceso Móvil:** PWA (Progressive Web App) que se conecta directamente a la API de Google Drive para leer/modificar el archivo.
- **Rendimiento:** Alta velocidad y bajo consumo de RAM, aprovechando los 32GB disponibles en PC pero optimizado para no generar cuellos de botella en renderizado web.

#### 4.2. Almacenamiento y Sincronización
- **Formato:** Archivo `.json` único (o fragmentado por años) para soportar fácilmente el anidamiento de subtareas.
- **Gestión de Conflictos:** El sistema debe validar el `ETag` o la fecha de última modificación (last_modified) del archivo en Drive antes de guardar un cambio. Si detecta que el archivo fue modificado externamente desde la última lectura, debe emitir una **alerta de conflicto** al usuario antes de sobrescribir.

#### 4.3. Flujo de Inteligencia Artificial (Offline-First)
- **Core Independiente:** El sistema funciona 100% sin conexión a APIs de LLM.
- **Diseño "AI-Ready":** La estructura del `.json` debe ser limpia y estandarizada. Esto permite al usuario exportar su base de datos, cargarla en un LLM externo (como asistente de organización), pedirle que reestructure prioridades o genere nuevas subtareas, y volver a importar el `.json` resultante al sistema. La GPU local de 2GB no procesará IA; se delega a modelos externos a elección del usuario mediante el intercambio de archivos.

### 5. Consideraciones para el LLM Agéntico (Desarrollador)
- **Stack Recomendado:** Frontend en HTML/CSS/JS (Vite/React o Vanilla modular para la PWA) y Backend en Python (FastAPI) o Node.js para servir localmente.
- **Gestión de Estado:** Implementar un validador de esquema estricto (ej. Pydantic o JSON Schema) para asegurar que si un LLM externo modifica el `.json`, este no rompa la aplicación al reimportarse.
- **Resolución de Conflictos:** Desarrollar un endpoint o función en la PWA que haga un "fetch" de metadatos de Drive antes del "push" (guardado).
